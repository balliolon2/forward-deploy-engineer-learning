FDE Mindset Principles

1. No Hallucination Without Citation
ในงาน Enterprise AI คำตอบที่ไม่มีหลักฐานอ้างอิงชัดเจนถือว่าใช้งานไม่ได้จริง การมี Citation ที่ชี้หน้าและท่อนข้อความตรงเป๊ะสำคัญกว่าความสวยงามของข้อความตอบ
2. Operational Actions > Analytics
FDE ไม่ได้สร้างแดชบอร์ดไว้นั่งดูตัวเลขเฉยๆ แต่สร้างเครื่องมือเพื่อให้เจ้าหน้าที่หน้างาน (Reviewer) กด Take Action (เช่น อนุมัติ, ตีกลับ, ปรับสถานะ) ได้ทันที
3. TDD on Ingestion & Edge Cases
ข้อมูลลูกค้าไม่เคยสมบูรณ์แบบเสมอ เราต้องใช้ Test-Driven Development ในการจำลองข้อมูลที่ขาดหายหรือผิดเพี้ยนไว้ล่วงหน้า

STAGE 01: Domain Modeling & Ubiquitous Language

เจาะลึกปรัชญา Domain-Driven Design (DDD) ในงาน Forward Deployed Engineering: ทำไมการนิยามภาษาให้คมชัดตั้งแต่ Day 1 ถึงเป็นตัวชี้ขาดความสำเร็จของ Enterprise AI

1. ในเชิงทฤษฎีคืออะไร? (The Engineering Theory)

💡 ปรัชญา Ubiquitous Language (Eric Evans, Domain-Driven Design)

ในงานวิศวกรรมซอฟต์แวร์ระดับองค์กร Ubiquitous Language คือภาษาหนึ่งเดียวที่เข้มงวดและทุกคนในโปรเจกต์ต้องใช้ตรงกัน ไม่ว่าจะเป็น Domain Expert (นักกฎหมาย, Compliance Officer), Software Engineer, Database Schema, Code Interface, และที่สำคัญที่สุดคือ LLM Prompts & Schemas

❌ สิ่งที่วิศวกรทั่วไปทำ (Mental Model หลุดขอบเขต)
  • เรียกทุกอย่างว่า "File", "Upload", "Ticket" ปะปนกัน
  • เอาคำศัพท์เทคนิค เช่น "Vector", "Chunk", "Prompt" ไปคุยกับลูกค้าหน้างาน
  • Prompt ให้ LLM สรุปแบบกว้างๆ ผลลัพธ์จึงแกว่งและไม่สอดคล้องกับระเบียบองค์กร
✅ สิ่งที่ Forward Deployed Engineer (FDE) ทำ
  • นิยาม Entity ชัดเจน: Dossier, Artifact, Criterion, Finding
  • แยก Bounded Context ชัดเจน: ฝั่งรับเอกสาร (Intake), ฝั่งตรวจเกณฑ์ (Evaluation), ฝั่งคนตัดสินใจ (Operation)
  • มีข้อห้ามชัดเจน (_Avoid_) ป้องกันคำกำกวมที่ทำให้ Agent หลงทาง

STAGE 02: Ingestion Pipeline & Document Normalization

เจาะลึกสถาปัตยกรรม Intake, Cryptographic Provenance, การแก้ปัญหา Messy Data และระเบียบ Test-Driven Development (TDD) ผ่าน Public Seam

1. ในเชิงทฤษฎีคืออะไร? (The Engineering Theory)

💡 ปัญหา "Garbage In, Hallucination Out" & Audit Trail ใน Enterprise

ในระบบ Compliance กฎหมายและหน่วยงานกำกับดูแล (Regulators เช่น ISO, Bank Audits) ต้องการความสามารถในการตรวจสอบย้อนกลับ (Auditability) 100% หากระบบ AI อ้างว่าคู่ค้าไม่ผ่านเกณฑ์ แต่ไม่สามารถบอกได้ว่าประโยคต้นฉบับอยู่ที่หน้าใด หรือหากเอกสารต้นฉบับถูกแก้ไขโดยไม่มีใครรู้ ระบบจะถือว่าไม่มีความน่าเชื่อถือทันที

❌ Flat Text Stream Approach (วิศวกรทั่วไป)

รวมเอกสาร 50 หน้าเป็น string ก้อนเดียว:

const rawDoc = "Page 1 text... Page 2 text...";

ข้อเสียร้ายแรง: เมื่อ AI ตรวจพบข้อผิดพลาด จะชี้พิกัดเลขหน้าไม่ได้ และไม่สามารถคำนวณ hash ยืนยันความถูกต้องของแต่ละหน้าได้

✅ Page-Indexed Provenance Bundle (FDE Approach)

แยกหน้าอย่างเป็นระบบ พร้อม SHA-256 Hash:

{
  artifactId: "art_001",
  pages: [{ pageNumber: 1, text: "..." }],
  contentHash: "e3b0c44298fc1c149afbf4c8996fb..."
}

ข้อดี: ทำ Citation ได้แม่นยำระดับหน้าและบรรทัด ทนทานต่อการถูก Audit และการันตีว่าเอกสารไม่ถูกดัดแปลง

2. การตัดสินใจทางสถาปัตยกรรม (ADR-0001 Deep Dive)

เราได้บันทึกการตัดสินใจใน docs/adr/0001-dossiers-as-immutable-page-indexed-bundles.md โดยมีเหตุผลสำคัญ 3 ประการ:

  • Immutability (Object.freeze): ข้อมูลเมื่อ Ingest เข้ามาแล้วต้องห้ามถูกแก้ไข (Read-only) เพื่อให้ทุกโมดูล downstream เห็นข้อมูลเดียวกันเสมอ
  • Cryptographic Hash per Artifact: คำนวณ SHA-256 จากข้อความที่เรียงลำดับตามเลขหน้า [page:N]text เพื่อใช้เป็น Fingerprint ยืนยันความถูกต้อง
  • Deterministic Sanitization: ลบ irregular whitespace และ newline (\r\n) ให้กลายเป็น single space ก่อนคำนวณ hash เสมอ เพื่อให้การคำนวณ Hash มีคุณสมบัติ Idempotent

3. ระเบียบวิธี TDD & Deep Module Seam

⚡ ทำไมต้องทดสอบที่ "Seam" (Public Interface)?

ในหนังสือ A Philosophy of Software Design โดย John Ousterhout: โมดูลที่ดีต้องเป็น "Deep Module" คือมี Interface ภายนอกที่เรียบง่าย แต่ซ่อนการทำงานที่ลึกซึ้งไว้ภายใน เราจึงทดสอบที่ Seam เดียวคือ ingestDossier(rawPayload) โดยไม่ไปผูกมัดกับฟังก์ชันย่อยข้างใน เพื่อให้เราสามารถรีแฟกเตอร์โค้ดภายในได้โดยที่เทสต์ไม่พัง

STAGE 03: Hybrid RAG & Exact Citation Engine

เจาะลึกวิศวกรรมการค้นหาสำหรับงานกำกับดูแล (Compliance RAG): ทำไม Vector อย่างเดียวถึงล้มเหลว, ทฤษฎี BM25 Lexical Ranking, การตัด Chunk ขอบเขตหน้า (Page-Bounded), และ Strict Verbatim Grounding

1. ในเชิงทฤษฎีคืออะไร? (The Engineering Theory)

💡 ทำไม Vector Semantic Search อย่างเดียวถึงตกม้าตายในงาน Compliance?

โมเดล Dense Vector Embeddings ถูกเทรนมาเพื่อจับ "ความหมายกว้างๆ (Semantic Similarity)" แต่ในโลกของสัญญาและข้อบังคับ กฎหมายมักขึ้นอยู่กับ ตัวเลขที่แน่นอน (Exact Numbers), รหัสมาตรฐาน (ISO 27001, SOC 2 Type II), และชื่อวรรค (Clause 5.1) ซึ่งบ่อยครั้งเวกเตอร์จะให้น้ำหนักคำพวกนี้น้อยมาก และดึงท่อนความหมายกว้างๆ ที่ไม่มีเลขข้อบังคับขึ้นมาแทน

❌ Vanilla Vector RAG (ค้นหาแบบทั่วไป)
  • ค้นหาคำว่า "ISO 27001 expiry" แต่อาจได้ท่อนสัญญาความมั่นคงปลอดภัยทั่วไปขึ้นมาแทน
  • ตัด Chunk ข้ามหน้า (Cross-page) ทำให้ไม่รู้ว่าวรรคนั้นจบหน้าไหน เริ่มหน้าไหน
  • ปล่อยให้ LLM อ้างอิงคำพูดโดยสรุป (Paraphrasing) ซึ่งไม่สามารถใช้เป็นหลักฐานทางกฎหมายได้
✅ Enterprise Hybrid RAG + Grounding (FDE Approach)
  • ใช้ BM25 Lexical Matching ให้ความสำคัญสูงสุดกับ Exact Keywords และ Acronyms
  • Page-Bounded Chunks: แต่ละ Chunk จะต้องอยู่ภายในหน้าของตัวเอง ไม่คร่อมหน้า
  • Strict Verbatim Verification: ตรวจสอบระดับ Substring ก่อนส่งให้ผู้ตรวจสอบ หากเพี้ยนแม้แต่คำเดียวจะถูกปฏิเสธ (Grounding Failed)

2. การตัดสินใจทางสถาปัตยกรรม (ADR-0002 Deep Dive)

เราได้บันทึกการตัดสินใจใน docs/adr/0002-page-bounded-chunking-and-verbatim-citations.md:

  • Page-Bounded Chunking Invariant: ห้าม Chunk ข้ามหน้าเอกสาร เพื่อรักษาพิกัด (artifactId, pageNumber, charOffset) สำหรับการ Audit
  • In-Engine BM25 Lexical Ranking: คำนวณ Inverse Document Frequency (IDF) และ Term Frequency (TF) แบบ Real-time เพื่อจัดอันดับคำค้นหาที่แม่นยำ
  • Zero Tolerance for Hallucinated Quotes: ฟังก์ชัน verifyCitation() จะสแกนหน้าเอกสารต้นฉบับจริง หากไม่เจอ Substring จะตัดสิทธิ์การเป็นหลักฐานทันที

3. ระเบียบวิธี TDD & โค้ดที่สร้างจริง (Seam: createCitationEngine)

⚡ สรุปผลการทดสอบ Vitest TDD 5/5 Passed

  artifactId: "art_msa",
  pageNumber: 2,
  exactQuote: "Vendor must retain all security audit logs for exactly 365 days"
});
expect(validResult.valid).toBe(true);

// 2. Rejecting Paraphrased Quote (LLM hallucination)
const paraphrasedResult = engine.verifyCitation({
  artifactId: "art_msa",
  pageNumber: 2,
  exactQuote: "Vendor shall keep security logs for one year" // Altered by LLM
});
expect(paraphrasedResult.valid).toBe(false);

// 3. Exact Acronym Retrieval (ISO 27001 matching)
const results = engine.retrieve("ISO 27001 certification standards", { topK: 1 });
expect(results[0].artifactId).toBe("art_iso_cert");
expect(results[0].text).toContain("ISO 27001");
🎯 FDE Battle Rule: "No Hallucination Without Citation"
ในองค์กรชั้นนำ การที่ AI ตอบคำถามสวยหรูแต่นิ้วชี้ไปผิดหน้า หรือโควทคำพูดเพี้ยนไปจากสัญญาตัวจริง มีค่าเท่ากับ ระบบพัง (System Failure) เพราะผู้บริหารหรือ Reviewer จะเซ็นอนุมัติบนหลักฐานที่บิดเบือนไม่ได้ สถาปัตยกรรม Stage 03 จึงเป็นการล็อกความปลอดภัยระดับ Codebase ก่อนที่เราจะเชื่อม LLM ใน Stage 04
Deep Dive & Theory

STAGE 04: Compliance Evaluation & Structured Finding Schema

เจาะลึกกระบวนการประเมินความสอดคล้องระดับองค์กร: ทำไม Binary Pass/Fail ถึงอันตราย, ไตรสถานะ Tri-State Findings, และระบบ Grounding Gatekeeper ที่สกัดกั้น Hallucinated AI Output

1. ในเชิงทฤษฎีคืออะไร? (The Engineering Theory)

💡 ปัญหาของ Binary Pass/Fail ในงานสัญญาระหว่างองค์กร

ในงานซอฟต์แวร์ทั่วไป วิศวกรมักมองเงื่อนไขเป็นบูลีน (True / False หรือ Pass / Fail) แต่ในงานกฎหมายและการตรวจสอบคู่ค้า (Compliance Auditing) เอกสารสัญญาจริงมักตกอยู่ในภาวะ "ข้อมูลไม่สมบูรณ์" หรือ "คลุมเครือ" (เช่น เอกสารสัญญาหน้า 10 พูดถึงการเก็บล็อก แต่ไม่ได้ระบุจำนวนวัน หรือระบุว่าขึ้นอยู่กับนโยบายลูกที่ไม่ได้แนบมาด้วย) การบังคับให้ระบบเลือกแค่ Pass หรือ Fail จะนำไปสู่หายนะด้าน Compliance ทันที

❌ Binary Classification (ระบบที่อันตราย)
  • ถ้าหาเอกสารไม่เจอ ➔ สรุปว่า Fail (สร้าง False Alarm ให้คู่ค้าไม่ผ่านเกณฑ์โดยไม่จำเป็น)
  • ถ้า AI เจอร่องรอยคำว่าล็อก ➔ สรุปว่า Pass (ปล่อยให้สัญญาที่มีช่องโหว่ทางกฎหมายหลุดรอด)
  • เชื่อใจข้อความที่โมเดลตอบโดยไม่ Re-verify Citation (เสี่ยงต่อ AI หลอนตัวเลข)
✅ Tri-State Taxonomy + Grounding Gate (FDE Approach)
  • Pass: พบหลักฐานชัดเจน และข้อความในสัญญาตรงตามเกณฑ์ 100%
  • Flagged: พบหลักฐานชัดเจน แต่ข้อความระบุชัดว่าละเมิดเกณฑ์ (เช่น สัญญาบอก 60 วัน เกณฑ์ขอ 180 วัน)
  • Inconclusive: ข้อมูลไม่เพียงพอ หรือ Citation ปลอม ➔ ส่งต่อไปยังคิว Reviewer มนุษย์ทันที

2. การตัดสินใจทางสถาปัตยกรรม (ADR-0003 Deep Dive)

เราได้บันทึกการตัดสินใจใน docs/adr/0003-schema-enforced-tri-state-findings-and-grounding-gate.md:

  • Strict Tri-State Schema: ทุก Finding ต้องมีสถานะ pass, flagged, หรือ inconclusive พร้อม confidence, reasoning, และ citations[]
  • The Grounding Gatekeeper Invariant: ไม่อนุญาตให้ Finding ใดคงสถานะ pass ได้เด็ดขาด หาก Citation ที่แนบมาไม่ผ่านการตรวจสอบแบบ Exact Substring ผ่าน verifyCitation()
  • Automated Downgrade to Inconclusive: เมื่อตรวจพบว่า AI อ้างอิงข้อความที่ไม่มีอยู่จริง ระบบจะลดระดับสถานะเป็น inconclusive พร้อมบันทึก [Grounding violation] ลงใน Audit Log ทันที
  • Strategy Pattern for Pluggable Evaluators: แยกระหว่าง Rule Evaluator (สำหรับ TDD/Local) และ LLM Client (สำหรับ Production)

3. ระเบียบวิธี TDD & โค้ดที่สร้างจริง (Seam: evaluateCompliance)

⚡ สรุปผลการทดสอบ Vitest TDD 3/3 Passed

เราทดสอบ Seam evaluateCompliance(dossier, policy, engine, evaluator) ใน 3 กรณีหลัก: (1) กรณีเอกสารผ่านเกณฑ์ 365 วัน ➔ pass, (2) กรณีสัญญาระบุ 60 วันซึ่งต่ำกว่าเกณฑ์ 180 วัน ➔ flagged, (3) กรณีจำลองโมเดล AI หลอน Citation ปลอม ➔ ถูก Grounding Gate สกัดจับและลดระดับเป็น inconclusive ทันที

src/evaluation/evaluate-compliance.test.ts Vitest Suite (3 Passed) 
// 1. Compliant Evidence Test
const passFindings = await evaluateCompliance(dossier, samplePolicy, engine);
expect(passFindings[0].status).toBe("pass");
expect(passFindings[0].groundingVerified).toBe(true);

// 2. Explicit Breach Test (60 days vs 180 days min)
const flaggedFindings = await evaluateCompliance(breachDossier, samplePolicy, breachEngine);
expect(flaggedFindings[0].status).toBe("flagged");
expect(flaggedFindings[0].reasoning).toContain("breaches minimum policy requirement");

// 3. Grounding Gate Interceptor (Hallucinated citation)
const rogueFindings = await evaluateCompliance(dossier, samplePolicy, engine, hallucinatingEvaluator);
expect(rogueFindings[0].status).toBe("inconclusive"); // Auto-downgraded from 'pass'!
expect(rogueFindings[0].groundingVerified).toBe(false);
expect(rogueFindings[0].reasoning).toContain("Grounding violation");
🎯 FDE Battle Rule: "Never Trust Raw LLM Output With Pass Status"
ความผิดพลาดอันดับ 1 ของทีมที่ทำ AI ในองค์กรคือการนำ output JSON ของ LLM มาใช้ตรงๆ โดยไม่มี Code-level Gatekeeper การมี Grounding Gate ดักจับแบบที่เราสร้างขึ้นนี้ คือสิ่งที่แยกความแตกต่างระหว่าง "เดโมของเล่น" กับ "ซอฟต์แวร์ระดับ Enterprise ที่ทนทานต่อการถูกตรวจสอบบัญชี (Audit-proof System)"
